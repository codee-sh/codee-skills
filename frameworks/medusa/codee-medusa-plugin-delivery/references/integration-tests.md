# Integration tests in the plugin

A plugin runs its HTTP and workflow integration tests in its own repository, against a test app made of
its `src` and a Docker Postgres, instead of in a project that installs it. The files are at the end of
this reference; replace `<plugin-name>`, `<plugin_name>` and the module placeholders.

## The parts

| File | Role |
|---|---|
| `medusa-config.ts` (root) | The test app: the plugin's own modules, and a test module when needed. |
| `docker-compose.test.yml` | Postgres 16 on `localhost:5432`, named after the plugin. |
| `jest.config.js` | A `TEST_TYPE` switch: unit by default, `integration:http`, `integration:modules`. |
| `integration-tests/setup.js` | Clears MikroORM's metadata, loads `.env.test`, and defaults `DB_HOST`, `DB_USERNAME`, `DB_PASSWORD` to the Docker values, so no credentials sit in a `.env`. |
| `integration-tests/utils/admin.ts` | `createAdminHeaders(container)`: an admin user and a token signed with `generateJwtToken` and the app's `jwtSecret` - no `jsonwebtoken` or `scrypt-kdf` dependency. |
| `integration-tests/http/<area>/<name>.spec.ts` | The HTTP and workflow tests, on `medusaIntegrationTestRunner`. |

The `package.json` scripts:

```json
"test:unit": "TEST_TYPE=unit jest --silent --runInBand",
"test:integration:http": "TEST_TYPE=integration:http NODE_OPTIONS=--experimental-vm-modules jest --silent --runInBand --forceExit",
"test:integration:modules": "TEST_TYPE=integration:modules NODE_OPTIONS=--experimental-vm-modules jest --silent --runInBand --forceExit",
"test:db:up": "docker compose -f docker-compose.test.yml up -d",
"test:db:down": "docker compose -f docker-compose.test.yml down -v",
"test:db:generate": "DATABASE_URL=postgres://postgres:postgres@localhost:5432/postgres medusa db:generate <moduleKey>"
```

## A test module, when the plugin owns no models

A plugin whose models live in its own module registers that module in `medusa-config.ts` and needs nothing
more. A plugin that works on a project's models - a CMS over a project's content module - needs a module
that plays that project's module:

```
integration-tests/modules/<test-module-name>/
├── index.ts          Module("<testModuleKey>", { service })
├── service.ts        MedusaService({ Test... }) - keys equal to the models' names
├── models/           one file per Test* model, flat: Medusa loads only the top of models/
├── <config>.ts       the plugin's options over the test models, when the plugin takes models in options
└── migrations/       generated by the user, committed with .snapshot-<test-module-name>.json
```

Unit tests import the same models and options from there, through a fixtures file in `src/**/__tests__/`
that only re-exports them, so both kinds of test share one source.

## Traps

- **A module path outside `src`** must be absolute. Medusa resolves a `./` path that does not start with
  `./src` inside `src` (`normalizeImportPathWithSource`); use `path.join(__dirname, "integration-tests/...")`.
- **The tables come from migrations.** `medusaIntegrationTestRunner` runs the modules' migrations, so a test
  module without them has no tables; `moduleIntegrationTestRunner` falls back to the models' schema.
- **`db:generate` needs a database.** It checks the connection before it diffs the models, and the test app
  has no `databaseUrl`, so without the script's `DATABASE_URL` it waits on
  `postgres://localhost/medusa-starter-default`.
- **Port 5432 only.** The runner cannot use another port; another Postgres there must stop.
- **Keep the test app out of the package.** Add `"integration-tests"` and `"medusa-config.ts"` to the
  `exclude` of `tsconfig.json`, which `medusa plugin:build` compiles, and keep them in the typecheck
  config. Check with `npx tsc -p tsconfig.json --noEmit --listFiles | grep -c -E "integration-tests|medusa-config"`,
  which must print `0`.

import path from "path"
import { defineConfig } from "@medusajs/framework/utils"

/**
 * The app the integration tests run: the plugin's own `src` - routes, workflows, subscribers - with its
 * modules, and, when the plugin owns no models, a test module that plays a project's module. It is not
 * part of the published package: tsconfig.json keeps this file and integration-tests/ out of the build.
 */
export default defineConfig({
  projectConfig: {
    http: {
      adminCors: "",
      authCors: "",
      storeCors: "",
      jwtSecret: "test",
      cookieSecret: "test",
    },
  },
  modules: {
    // The plugin's own module, with the options a project would pass:
    // <moduleKey>: {
    //   resolve: "./src/modules/<module-name>",
    //   options: {},
    // },
    //
    // A test module outside src needs an absolute path: Medusa resolves a "./" path that does not start

### `docker-compose.test.yml`

```yaml
services:
  postgres-test:
    image: postgres:16-alpine
    container_name: <plugin-name>-test-db
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: postgres
    ports:
      - "5432:5432"
    volumes:
      - <plugin_name>_test_db:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  <plugin_name>_test_db:
```

### `jest.config.js`

```js
module.exports = {
  transform: {
    "^.+\\.[jt]s$": [
      "@swc/jest",
      {
        jsc: {
          parser: { syntax: "typescript", decorators: true },
        },
      },
    ],
  },
  testEnvironment: "node",
  moduleFileExtensions: ["js", "ts", "tsx", "json"],
  modulePathIgnorePatterns: ["dist/", "<rootDir>/.medusa/"],
}

if (process.env.TEST_TYPE === "integration:http") {
  module.exports.testMatch = ["**/integration-tests/http/**/*.spec.[jt]s"]
  module.exports.setupFiles = ["./integration-tests/setup.js"]
} else if (process.env.TEST_TYPE === "integration:modules") {
  module.exports.testMatch = [
    "**/src/modules/*/__tests__/**/*.integration.spec.[jt]s",
  ]
  module.exports.setupFiles = ["./integration-tests/setup.js"]
} else {
  module.exports.testMatch = ["**/__tests__/**/*.unit.spec.[jt]s"]
}
```

### `integration-tests/setup.js`

```js
const { MetadataStorage } = require("@mikro-orm/core")
const { loadEnv } = require("@medusajs/framework/utils")

MetadataStorage.clear()
loadEnv("test", process.cwd())

// The test runner creates and drops a database per run through these; they match docker-compose.test.yml.
process.env.DB_HOST ??= "localhost"
process.env.DB_USERNAME ??= "postgres"
process.env.DB_PASSWORD ??= "postgres"
```

### `integration-tests/utils/admin.ts`

```ts
import type {
  ConfigModule,
  IAuthModuleService,
  IUserModuleService,
  MedusaContainer,
} from "@medusajs/framework/types"
import {
  ContainerRegistrationKeys,
  Modules,
  generateJwtToken,
} from "@medusajs/framework/utils"

const ADMIN_EMAIL = "admin@plugin.test"

/**
 * Creates an admin user and signs a token for it with the app's JWT secret.
 *
 * @param container - The test app's container.
 * @returns Request options carrying the admin's bearer token.
 */
export const createAdminHeaders = async (container: MedusaContainer) => {
  const user = await container
    .resolve<IUserModuleService>(Modules.USER)
    .createUsers({ email: ADMIN_EMAIL })
  const authIdentity = await container
    .resolve<IAuthModuleService>(Modules.AUTH)
    .createAuthIdentities({
      provider_identities: [{ provider: "emailpass", entity_id: ADMIN_EMAIL }],
      app_metadata: { user_id: user.id },
    })
  const { jwtSecret } = container.resolve<ConfigModule>(
    ContainerRegistrationKeys.CONFIG_MODULE
  ).projectConfig.http

  const token = generateJwtToken(
    {
      actor_id: user.id,
      actor_type: "user",
      auth_identity_id: authIdentity.id,
      app_metadata: { user_id: user.id },
    },
    { secret: jwtSecret, expiresIn: "1d" }
  )

  return { headers: { authorization: `Bearer ${token}` } }
}
```

### `docs/tests.md`

The user-facing guide. Keep the sentence inside the `TEST MODULE` comment only when the plugin has a test module, and remove the comment markers.

````markdown
# Tests

How the plugin's tests run, and where a new one goes. Which test a change owes is decided by the
`codee-medusa-testing` skill.

## Unit tests

```bash
yarn test:unit
```

Colocated as `src/**/__tests__/<name>.unit.spec.ts`. They need no database.

## Integration tests

They boot a Medusa app with a real Postgres, so they run manually, when the risk is real. One cycle:

```bash
yarn test:db:up                 # Postgres 16 in Docker on localhost:5432
yarn test:db:generate           # only after a change to a test model - the user runs it
yarn test:integration:http      # integration-tests/http/**/*.spec.ts
yarn test:integration:modules   # src/modules/*/__tests__/**/*.integration.spec.ts
yarn test:db:down               # stop it and drop its volume, freeing port 5432
```

An agent may run the cycle on its own, except `yarn test:db:generate`, and stops only a database it
started - see `AGENTS.md`, "Validation Commands".

`medusaIntegrationTestRunner` creates a database per run and drops it afterwards. It reaches Postgres
through `DB_HOST`, `DB_USERNAME` and `DB_PASSWORD`, which `integration-tests/setup.js` sets to the values of
`docker-compose.test.yml` unless the environment or a `.env.test` file says otherwise. The runner always
connects on port `5432`, so stop any other Postgres listening there.

### The test app

The app is `medusa-config.ts` in the plugin's root. It loads the plugin's own `src` and its modules<!--
TEST MODULE: keep the rest of this sentence when the plugin has one -->, and a test module in
`integration-tests/modules/<test-module-name>/` that plays a project's module<!-- END -->. None of it is in
the published package; `tsconfig.json` keeps both out of the build.

### Migrations

`medusaIntegrationTestRunner` creates the tables through the modules' migrations. The user generates them,
from the plugin's root, with the test database up:

```bash
yarn test:db:generate
```

`db:generate` checks the connection before it diffs the models against the snapshot, and the test app has
no `databaseUrl`, so the script points it at the Docker Postgres. It writes nothing to the database.
Regenerate after any change to a model, and commit the migration together with its `.snapshot-*.json`.

### Writing one

- An HTTP test goes to `integration-tests/http/<area>/<name>.spec.ts`; a workflow test sits next to the
  route that runs it, or in its own file there.
- `createAdminHeaders(container)` from `integration-tests/utils/admin.ts` signs an admin token for
  `/admin` routes.
- Each file sets `jest.setTimeout(60 * 1000)` and says in its JSDoc that it is a manual run.
````
